# 已经授权了，为什么还提示"该目录尚未授权"？

> 现象：在 **应用中心 → CAD 看图 → 设置 → 访问权限** 里明明加了目录、也保存了，
> 但双击图纸或打开图纸库仍提示「该目录尚未授权」，目录列表也是空的或者只有一个
> 名字很奇怪、点进去就报错的文件夹。

## 结论

这是 **1.0.2 及更早版本的 bug**，1.0.3 已修复：飞牛把多个目录**用冒号拼成一个
字符串**传给应用，而旧版只按逗号切分，于是整串被当成**一个**路径。拿现场的实际
数据看最直观（用户在界面上授权了「售前项目」一个目录，应用包又自带一个共享目录）：

```jsonc
// cmd/main 把两者拼起来交给服务端（和 PATH 一样，冒号分隔）：
//   TRIM_DATA_ACCESSIBLE_PATHS = /vol1/1000/售前项目
//   TRIM_DATA_SHARE_PATHS      = /vol1/@appshare/fnos-dwg-viewer/drawings
//   → ALLOW_PREFIXES           = /vol1/1000/售前项目:/vol1/@appshare/fnos-dwg-viewer/drawings

// 旧版只按逗号切分 → 得到 1 个"路径"，它根本不存在：
"allowedRoots": ["/vol1/1000/售前项目:/vol1/@appshare/fnos-dwg-viewer/drawings"]
//                       ↑ 这里本来是分隔符，被当成了路径的一部分

// 1.0.3 同时认 , ; : 三种分隔符 → 得到真正的 2 个目录：
"allowedRoots": ["/vol1/1000/售前项目", "/vol1/@appshare/fnos-dwg-viewer/drawings"]
```

白名单里躺着这么一根不存在的字符串，任何真实路径都不在它"里面"，
所以**所有**目录都被判为未授权——表现就是"授权了也没用"。

同时，图纸库里那个唯一的"文件夹"其实是从这根字符串上 `basename()` 出来的
（末尾是 `drawings`），点进去自然打不开。

## 怎么自查（1.0.3 起）

浏览器直接打开：

```
http://<飞牛IP>:8020/api/config
```

重点看两个字段：

| 字段 | 期望 | 含义 |
| --- | --- | --- |
| `env.rawAccessiblePaths` | 形如 `/vol1/1000/售前项目`，多个目录之间是 `:` | 飞牛传下来的**原始**授权目录串 |
| `allowedRoots` | 每个真实目录**各占一项**，且都能在文件管理器里找到 | 应用解析后的白名单 |

如果 `allowedRoots` 里出现带冒号的"长路径"，就是本文描述的问题（请升级到 1.0.3）。

## 1.0.3 的额外兜底

升级后即使再遇到奇怪的输入也能自愈（每一步都必须落在白名单内，不会放开越权）：

1. 原样尝试；
2. 带冒号的整串 → 按冒号切开，逐段尝试；
3. 请求路径被百分号编码过（文件管理器偶发二次编码）→ 解码后再试；
4. 目录已不存在（被改名/删除）→ 退到最近一个真实存在的上级目录，并把
   修正后的路径回传给前端。

## 还需要注意的点

- **授权后必须重启应用**：授权目录是进程启动时读取的环境变量。1.0.4 起
  由 `cmd/config_callback` 负责在保存设置后自动重启，不会再出现"改完授权
  应用变已停用"的情况。
- **要授权到目录，不要选到文件**：选中具体文件等于只授权了那一个文件，
  双击同级图纸仍会提示未授权。
- **应用自带的共享目录**：1.0.2 及更早版本在访问权限列表里会有一条灰色的、
  无法删除的「应用文件/fnos-dwg-viewer/drawings」，那是应用包自己声明的共享目录
  （`config/resource` → `data-share`）。本应用用不到它，**1.0.3 已去掉声明**，
  该条目不会再出现。

# 第二种情况：授权了，但"有的子文件夹打得开、有的打不开"

> 现象（1.0.4 现场反馈）：`售前项目` 这个目录已经在访问权限里了，图纸库也能
> 列出它，可是点进某些子文件夹就报
> **「没有读取权限：undefined」**，另一些子文件夹却完全正常。

## 结论：这是**文件系统权限**问题，不是应用的路径解析问题

飞牛给**每一个**原生应用都建了专属系统账号（本应用是 `fnos-dwg-viewer`），
应用进程就以这个身份运行；而"我的文件"里的数据归**你本人的账号**所有。
`访问权限` 的作用是把这个目录的 ACL 授给应用账号。

问题在于**这条 ACL 有没有递归到子目录**：

- 如果只给 `售前项目` 本身加了 ACL —— 目录能列出来；
- 但**已有的**子目录（`2026年06月`、`遂宁项目图纸`…）没有对应 ACL → 读不进去；
- 而在授权**之后新建**的子目录会继承默认 ACL（`-d`）→ 反而是好的。

于是表现就是时好时坏、"有的能显示、有的显示不出来"。
另外，从低版本升级到 fnOS v1.2+ 时，存储空间要完成一次**权限转换**
（系统设置 → 存储空间管理，显示「权限未适配」就是没转），
官方明确说未转换期间"**应用可能无法正常访问已授权的文件夹**"。

## 怎么定位（1.0.4 起）

应用内置了权限体检，三种入口：

1. 图纸库里报错时点 **权限诊断** 按钮；
2. 直接打开 `http://<飞牛IP>:8020/api/doctor`；
3. 看 `http://<飞牛IP>:8020/api/config` 里的 `appUser`（应用运行账号）。

`/api/doctor` 会给出：

| 字段 | 说明 |
| --- | --- |
| `appUser` / `uid` / `runsAsRoot` | 应用是以谁的身份在跑（`setfacl` 命令里的账号就是它） |
| `roots[].listable` | 该授权目录当前能不能列 |
| `roots[].blockedBy` | **从根往下第一个"进不去"的祖先目录** —— 根因就在这一层 |
| `fixCommands` | 按现场目录拼好的、可直接复制执行的修复命令 |

## 修复（按顺序试）

1. **官方入口**：系统设置 → 应用 → CAD 看图 → 把存放图纸的文件夹加进可访问范围
   （仅管理员可操作）。这是 fnOS 给的标准做法，优先用它。
2. **先做权限转换**：系统设置 → 存储空间管理，如果有「权限未适配」的存储空间，
   先按提示完成一次转换，再回到上面重新授权一次。
3. **SSH 一次性补齐**（社区里验证过的办法）。在 系统设置 → SSH 启用后用终端登录：

   ```bash
   # 把应用账号递归授到整棵目录树（-R），并让以后新建的子目录也继承（-d）
   sudo setfacl -R    -m u:fnos-dwg-viewer:rwx "/vol1/1000/售前项目"
   sudo setfacl -R -d -m u:fnos-dwg-viewer:rwx "/vol1/1000/售前项目"

   # 确认结果：应该能看到 user:fnos-dwg-viewer:rwx 这一行
   getfacl "/vol1/1000/售前项目"
   ```

   账号名以 `/api/doctor` 里的 `appUser` 为准。改动权限后回图纸库点 ⟳ 即可，
   **不需要重启应用**。

4. **完全不动目录权限：改用 WebDAV**。左侧切到「WebDAV」，填飞牛地址
   （`http://<IP>:5005`）和你的登录账号即可 —— 它走的是你自己的账号权限，
   不需要任何目录授权，账号能看到什么就能打开什么。勾上「记住连接信息」后，
   应用重启/升级都不用重填。

5. ~~**或者换 root 权限版**：`npm run fpk:root` 产出的包……~~ —— 1.0.7 起只有一个包，
   它本身就是 `run-as: root`，`npm run fpk:root` 脚本与 `-root.fpk` 产物名都已删除。

## 为什么错误提示里曾经是 `undefined`

1.0.3 及更早：`listLocal` 里 `readdir`/`stat` 抛错后，异常直接冒泡到顶层
`toApiError(err)`，没有把"哪个路径"传下去，于是拼出
`没有读取权限：undefined`。1.0.4 起所有可能抛 FS 错误的地方都带上了真实路径，
并在错误体里一并返回 `path` / `appUser` / `fixCommand`。

## 升级

> 1.0.7 起只有一个包：`release/fnos-dwg-viewer-1.0.7.fpk`（不再有 `-root` 后缀版本）。
> 覆盖安装后**到应用中心停止再启动一次**，让 root 身份生效。

安装 `release/fnos-dwg-viewer-1.0.6.fpk`（应用中心 → 手动安装），
它会覆盖安装并保留已有的访问权限设置、WebDAV 连接信息和按需授权记录。
装完如果应用显示"已停用"，点一次「启动」即可（1.0.4 已修掉这个状态卡死的问题）。

> 用 root 权限版的话，请改用 `fnos-dwg-viewer-1.0.6-root.fpk`：
> **1.0.5 的 root 版是坏的**（装了也照样提示未授权），详见
> 本文档最后一节「第四种情况」。

# 第三种情况：根本不想配授权目录（1.0.5 起）

## 结论：可以直接在应用里点一下，不用去系统设置

飞牛给**网页应用**提供了官方 SDK `@trimjs/web-app`，其中的
`pickUserFile` / `authorizeUserFile` 是宿主级的**按需授权**接口：

- `pickUserFile({ directory: true })` —— 弹出飞牛自己的文件选择器，选中的文件夹
  当场授权给本应用；
- `authorizeUserFile(path)` —— 把指定目录（比如你双击进来的那个）就地授权。

这就是飞牛自家「文档」等第一方应用**没有"访问权限"设置项**的原因 ——
它们用的就是这套接口。本应用 1.0.5 也接上了，入口在：

- 图纸库左上角（未授权时）/ 错误提示框里 → **「从飞牛选择文件夹」**、**「授权这个目录」**
- 双击图纸打不开时的提示卡片里 → 同上

## 为什么有时候看不到这两个按钮

按需授权依赖**宿主桥接**，只有在本应用跑在**飞牛桌面的应用窗口**里才有。
SDK 的初始化逻辑（读 `node_modules/@trimjs/web-app/dist/index.js` 可确认）分三种情况：

| 环境 | 判定 | 结果 |
| --- | --- | --- |
| 飞牛桌面 iframe | `window.parent !== window` 且与父窗口握手成功 | 方法表由**宿主**声明，宿主给了就有 |
| 飞牛浏览器扩展 | 上面握手失败、但扩展宿主在 | `pickFile` 可用；`pickUserFile` / `authorizeUserFile` 抛 `NotSupportedInExtensionHost`（拿不到操作系统的文件权限） |
| 独立网页 / Docker | `window.parent === window` → `isStandaloneWeb` | 初始化直接短路，**不建立任何桥接** |

所以用浏览器新标签页直接打开 `http://飞牛IP:8020` 时，这两个按钮一定不在。
此时点按钮旁边的 **「为什么？」**，会展开一段诊断信息：

```
宿主桥接   在飞牛桌面窗口内：否；SDK 加载：未加载；握手完成：否
独立网页   否
宿主标识   (父窗口没有告知应用名)
宿主平台   (未知)
选择文件夹  不可用；授权目录：不可用
```

把这段贴出来就能定位（它同时也打在浏览器控制台里，前缀 `[fnos]`）。

## 授权之后应用是怎么"记住"的

两件事要区分开：

1. **操作系统层面的权限** —— 由飞牛宿主负责，把本应用的系统账号
   （`fnos-dwg-viewer`）加进目标目录的 ACL。这一步是宿主做的，应用管不着。
2. **本应用自己的白名单** —— 应用默认只读「应用设置 → 授权目录」里的路径，
   飞牛改了 ACL 但**没有**改这份列表。所以前端会把授权结果回传给
   `POST /api/grant`，登记到 `TRIM_PKGVAR/granted.json`。

如果只做第 1 步不做第 2 步，现象就是"飞牛说授权成功了，应用里照样打不开"。

服务端登记时会**先验证现在真的读得动**（`stat` + `access(R_OK|X_OK)`），
不通过就拒绝并说明原因。因此这个接口无法用来提权 —— 它只能把已经存在的权限记下来。

想撤销：权限诊断面板里对应目录旁边有 **「撤销」**，或者直接删掉
`granted.json` 里那一条。撤销只清本应用白名单，**不会**回收系统 ACL
（那个请去系统设置里操作）。

## 相关接口（1.0.7 已全部删除）

| 接口 | 作用 |
| --- | --- |
| `GET /api/grant` | 看当前登记了哪些按需授权路径 |
| `POST /api/grant` `{paths:[...]}` | 登记（只接受绝对路径 + 真实可读的目录；传文件路径会归到它所在目录） |
| `DELETE /api/grant?path=...` | 撤销一条 |

> 1.0.7 起这三个接口连同 `TRIM_PKGVAR/granted.json` 一起删掉了，访问返回 404。

# 第四种情况：装了 root 权限版，双击图纸还是提示"这个目录还没授权"（1.0.5 → 1.0.6）

## 现象

用 `fnos-dwg-viewer-<版本>-root.fpk` 安装，从文件管理器双击 `.dwg` / `.dxf`，
应用却弹出「打不开：这个目录还没授权」，并引导你去「系统设置 → 应用」配授权目录。
明明装 root 版就是为了不配这个。

## 根因：包改成了 root，代码没跟着改

1.0.4 引入了 `run-as: root` 的 root 权限版（`npm run fpk:root`，见 README 3.3），
但 **1.0.5 的服务端仍然只有一套逻辑**：

```js
function isAllowed(abs) {
  const roots = allowedRoots()          // ← 授权目录列表
  if (roots.length === 0) return isInside(abs, ROOT)
  ...
}
```

而 root 版压根没配过授权目录，`roots` 是空的，于是所有用户文件路径都被
`OUT_OF_SCOPE` 拦下。**进程其实早就有 root 身份、什么都读得到**，
拦住它的是应用自己那份白名单 —— 这跟操作系统权限一点关系都没有。

也就是说：**"包是不是 root 版"和"进程有没有拿到 root"是两件事，代码必须看后者。**

## 1.0.6 怎么修的

判定改成只看运行期真实身份：

```
UNRESTRICTED = (process.getuid() === 0) || FNOS_ACCESS_MODE ∈ {all, root, ...}
```

- `UNRESTRICTED` 为真时，`isAllowed()` 直接返回 `true`，不再有白名单；
- 图纸库的浏览根自动取 `/vol1`、`/vol2` …（界面上显示「存储空间 1」）；
- 拿不到 `/volN`（比如非 Linux）时退化成文件系统根，并且**不会再叠一层虚拟根**
  ——否则虚拟根里会列出一个指向自己的"根目录"，点进去原地打转。

## 怎么确认现在是哪一种

> ⚠️ 下表描述的是 **1.0.6** 的界面。1.0.7 起这些提示条全部删除了 ——
> 现在只有一种模式，界面上不再显示运行模式；要确认身份看 `/api/config`
> 的 `accessMode` / `runsAsRoot`。

看图纸库顶部那一行：

| 显示 | 含义 | 该做什么 |
| --- | --- | --- |
| 绿色「全盘模式：… 不需要授权目录」 | root 生效，一切正常 | 不用管 |
| 黄色「本包是『root 权限版』，但服务没有以 root 运行（当前账号 xxx）」 | 系统没让本应用以 root 跑 | ① 确认装的是文件名带 `-root` 的包；② 到应用中心**停止再启动**（root 只在重新拉起进程时生效）；③ 仍然这样就按需授权 / 配授权目录 / 用 WebDAV |
| 什么都不显示 | 普通包，按授权目录模式 | 见本文档前三种情况 |

更细的数据在 `http://飞牛IP:8020/api/config`：`accessMode`（`root` / `scoped`）、
`unrestricted`、`runsAsRoot`、`uid`、`rootVariant`、`storageRoots`。
`/api/doctor` 里的 `hints` 也会直接写出结论。

> 为什么会分不清：飞牛对 `run-as: root` 的限制只针对**发布到官方应用中心**
> （仅合作企业可以）。手动安装的第三方包是否放行取决于系统版本，
> 所以不能假设"装了 root 版就一定有 root"。

## 为什么不用"包名/标记文件"来判断权限

包身份很容易骗人：包是 root 版但系统没照做时，代码会以为"不用授权了"，
用户却什么也读不到，还看不到任何提示。

所以：

- **权限判定**一律用 `process.getuid()`；
- 包里那个 `app/server/ROOT_VARIANT` 标记文件**只用来解释**"root 没生效"，
  绝不参与放行决策。

## 顺带一提：`FNOS_ACCESS_MODE=all`

Docker 部署（把整个存储挂进容器）或想手动验证全盘模式时，可以设
`FNOS_ACCESS_MODE=all` 强制进入全盘模式。注意它**不会**让进程获得额外权限：
如果容器里的进程本来就读不到某个路径，设了它只会把错误从
「该目录尚未授权」变成「没有读取权限」—— 那才是真正的权限问题。
`/api/doctor` 会在这种情况下明确提示这一点。
