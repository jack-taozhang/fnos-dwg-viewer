# 常见问题与排查（1.0.9）

> 1.0.7 起**只有一种模式**：安装包声明 `run-as: root`，服务进程直接读全部存储空间。
> 没有「授权目录」、没有「按需授权」、界面上也不再有跟授权有关的任何提示。
> 遇到问题基本都不是"权限没配"，而是**挂载、文件本身，或者进程没拿到 root**。
>
> 1.0.8 把「本机存储」顶层改回了 1.0.6 的形态：**直接列出各个存储空间**
> （显示成「存储空间 1」「存储空间 2」），不再在应用里分「我的文件 / 团队文件 /
> 外接存储 / 远程挂载 / 应用文件」。
>
> **1.0.9 把应用收窄成纯粹的「打开方式」**：取消桌面图标、删掉应用内的「图纸库」
> 文件浏览抽屉与悬浮按钮、界面上不再有任何应用自带的顶栏或侧栏，
> 并从"在飞牛桌面窗口里打开"改为**浏览器新标签页打开**。
> 所以本文里凡是提到"图纸库抽屉 / 悬浮按钮 / 桌面图标"的内容都已随之删除，
> 相关的排查见第 7 节与第 11 节。
>
> 想了解当年那两套授权机制的来龙去脉，看 [`history-authorization.md`](history-authorization.md)（历史存档）。

## 0. 先看现场：两个只读接口

浏览器直接打开（`<IP>` 换成飞牛地址，端口默认 `8020`）：

| 接口 | 看什么 |
| --- | --- |
| `/api/config` | `accessMode`（应为 `root`）、`unrestricted`（应为 `true`）、`runsAsRoot` / `uid`、`sources`（顶层清单，就是各存储空间）、`storageRoots`（探测到的挂载点）、`env`（飞牛传下来的原始环境变量） |
| `/api/doctor` | 逐个存储空间体检：`roots[].listable`（能不能列）、`roots[].blockedBy`（**从根往下第一个进不去的祖先目录**，根因就在这一层）、`hints`（结论） |

> ⚠️ 界面上**不再有**「权限诊断」按钮了（原来在图纸库抽屉里的错误面板上，随抽屉一起删掉）。
> 现在要看这两份数据，**直接在浏览器地址栏打开对应的 URL** 即可。

`/api/grant` 在 1.0.7 已删除，访问返回 404 —— 那是正常的。
`/api/list`（列目录）仍然在，但 1.0.9 起界面不再调用它，只留作排障入口。

## 1. 应用中心里显示「已停用」，点启动才起来

1.0.4 起已修掉"保存设置后应用卡在停用"的问题。若仍遇到，**点一次「启动」**即可。
测试机/模拟器上如果是刚安装完没点启动，也属正常。

## 2. 双击图纸 →「打不开：这个位置不在可访问范围内」

这是**唯一**会导致这种情况的原因：服务进程落在了应急的按目录白名单模式
（`FNOS_ACCESS_MODE=scoped`），或它**没拿到 root**。正常安装不会这样。

处理顺序：

1. 应用中心 → 「CAD 看图」→ **停止**，再 **启动**。
   root 身份只在进程重新拉起时才生效，升级后不重启是最常见的原因。
2. 打开 `/api/config` 看两个字段：
   * `accessMode` 是 `scoped` → 有人手工设了 `FNOS_ACCESS_MODE`，去掉再重启；
   * `runsAsRoot` 是 `false` 且 `uid` 不是 `0` → 系统没让本应用以 root 运行。
     确认装的是最新包（`config/privilege` 里应是 `run-as: root`），并重启过。
3. `/api/doctor` 的 `hints` 会把结论直接写出来，照它说的做。

> **为什么权限判定看运行期 uid 而不是"包是不是 root 版"**：
> 飞牛的 `run-as: root` 是让 `cmd/` 里的生命周期脚本以 root 执行，node 进程随之拿到
> root；包里的声明只能用来写提示。1.0.5 就是把这两件事搞混了 —— 包已经是 root 版、
> 进程也真有 root，代码却仍按"白名单为空 → 全部拦下"处理，于是双击什么都打不开。
> 现在 `isAllowed()` 只看 `UNRESTRICTED`，而它由 `FNOS_ACCESS_MODE` 决定。

## 3. `/api/list` 顶层是「存储空间 1 / 2」，不是飞牛的「我的文件 / 团队文件」

**这就是预期的样子**（1.0.8 起）。顶层列的是**各个存储空间的挂载点**
（`/vol1` → 「存储空间 1」、`/vol00` → 「存储空间 00」），点进去就是那个卷的原始目录：

```
存储空间 1
├── 1000/          ← 你自己的"我的文件"（数字是 uid）
├── 1001/          ← 另一个用户的"我的文件"
├── @team/         ← 团队文件
├── @appshare/     ← 应用共享文件夹
├── @appdata/      ← 应用运行期数据
└── 你自己建的共享文件夹/…
```

飞牛的「我的文件 / 团队文件 / 外接存储 / 远程挂载 / 应用文件」是**文件管理应用里**的
入口分类。1.0.7 曾经照搬过一套到本应用里，1.0.8 撤回了 —— 飞牛已经分好了，
应用里再分一套只是多一层要维护、且跟不上系统变化的映射（卷怎么切、哪个算外接盘
是系统的事，应用不该替它判断）。

顶层条目是快照式的：`/api/config` 的 `sources` 数组（每条 `{label, path}`）
与 `storageRoots` 对得上，说明探测没漏。

> 1.0.9 起这一层**在界面上已经看不到了**（文件浏览已删）。想核对执行上面的接口即可。

## 4. 「存储空间 1」的编号和飞牛界面里对不上

编号直接取自挂载点：`/vol1` → 「存储空间 1」，`/vol2` → 「存储空间 2」，
外接盘是两位数的 `/vol00` → 「存储空间 00」。

所以：

* **跳号是正常的**。只有 `/vol2` 就只会出现「存储空间 2」—— 系统就是这么挂的，
  应用原样列出，不会替它重新编号（重编号反而会和你 SSH 进去看到的路径对不上）。
* **外接盘显示成「存储空间 00」而不是"外接存储"** —— 它在系统里本来就是一个
  独立的卷，应用不再替你去猜"这算不算外接盘"。
* 想看应用到底认了哪些路径，直接打开 `/api/config` 看 `storageRoots`。

## 5. 某个存储空间压根没出现在 `/api/list` 顶层

`detectStorageRoots()` 默认扫 `/` 下形如 `/volN` 的挂载点。
没出现的可能原因：

* 该存储空间**没有挂载**（系统设置 → 存储空间管理里能看到状态）；
* 从低版本升级到 fnOS v1.2+ 后**还没做权限转换**（显示「权限未适配」）；
* Docker 部署时没有把宿主目录挂进容器 —— 这时请用 `LOCAL_ROOT`（见 README 第八节）或
  显式指定 `FNOS_VOL_ROOTS`。

## 6. 点进去 →「打不开：这个位置读不进去」（EACCES）

**这不是授权问题**：root 也能遇到读不进去的位置。常见原因是这个位置所在的
磁盘/共享是只读的、已断开，或尚未挂载完成。

1. 系统设置 → 存储空间管理，确认该存储空间状态正常（不是已卸载 / 已降级）；
2. 外接盘 / 远程挂载：确认设备插好、连接没断（远程挂载断了以后目录会变成空或报错）；
3. 确认完后点错误卡片上的 **「重试」**。

> root 模式下 `eaccesError()` **不会**再给 `setfacl` 修复命令。加 ACL 解决不了
> 坏挂载和只读介质，照抄只会改坏系统权限。只有 `FNOS_ACCESS_MODE=scoped` 时才会给。

## 7. 为什么应用里没有文件浏览（图纸库 / 抽屉都没了）

**这是刻意设计，而且 1.0.9 起连抽屉本人都删了。**

* 1.0.7：抽屉改为**默认收起**（双击进来看的就是那张图，左边再挂一个三百多像素的
  抽屉很碍事），想看别的图纸点图面左上角的「图纸库」按钮。
* **1.0.9：抽屉和那个按钮整体删除。**

删掉的理由是**职责重叠**：本应用已经收窄成纯粹的「打开方式」，入口只有
"文件管理器里双击"这一条；再放一棵文件树，就等于在应用里复刻一个只读的文件管理器
—— 而用户已经有飞牛自己的文件管理了，那才是这个职责的正主。
顺带也没有了"应用内部再套一层导航"的问题。

**想看别的图纸怎么办？** 回飞牛的文件管理，双击另一张。

**直接打开 `http://<IP>:8020`（不带 `?path=`）会看到什么？**
一张说明卡片（"没有指定要打开的图纸"），告诉你本应用只用来打开文件。
这是正常的 —— 应用已经没有"空手进来也有东西可看"的形态了。

## 8. 外接盘 / 远程挂载的图纸打得开吗？

能 —— root 进程读的是真实文件系统路径，不区分"内部卷还是外接盘"。
U 盘、移动硬盘、rclone / cifs / nfs 的远程挂载，只要**系统层面挂上了**，
它的挂载点就会像别的卷一样出现在顶层（外接盘通常是 `/vol00`、「存储空间 00」）。

打不开时按第 6 节处理：多半是设备拔了、挂载断了或只读。

> 1.0.7 曾在应用里单独识别"外接存储 / 远程挂载"两类（读 `/proc/mounts` +
> sysfs 判断可移除设备），1.0.8 已撤掉：**哪些算外接盘是系统的事**，
> 应用跟着系统挂载点走永远不会错。相应的 `FNOS_PROC_MOUNTS` 开关与
> `/api/doctor` 里的 `mountsFile` 字段也一并移除。

## 9. 那旧的那两套机制去哪了？

1.0.7 把它们**整体删掉**了，包括：

* 「系统设置 → 应用 → CAD 看图 → 访问权限」这个设置项 —— 用
  `disable_authorization_path=true` 让应用中心不再显示；
* 界面上的「授权这个目录 / 从飞牛选择文件夹 / 撤销」按钮、黄色的
  "本包是 root 权限版但没以 root 运行"提示条、绿色的「全盘模式」提示条；
* `POST /api/grant` 接口与 `TRIM_PKGVAR/granted.json`；
* `@trimjs/web-app` 依赖、`npm run fpk:root` 脚本、`-root.fpk` 产物名、
  `app/server/ROOT_VARIANT` 标记文件。

如果你按老文档在找这些东西，看 [`history-authorization.md`](history-authorization.md)。

另外 1.0.7 短暂存在过的「本机存储分类入口」（`detectLocalSources()`）也在 1.0.8 撤掉了，
见第 3 节。

## 11. 双击图纸后**嵌在飞牛桌面窗口里**打开，不是浏览器新标签页

这是 1.0.9 要改掉的行为，靠 `cmd/fix-open-type` 在装完 / 改设置 / 升级后改数据库实现。
如果还是嵌在桌面窗口里，说明那个脚本没跑成。

**根因**：应用中心对第三方包**只会建 `iframe` 型服务**（硬编码，不读
`app/ui/config` 里的 `"type": "url"`）；而飞牛前端是按这个字段分流的 ——
`type === 'url'` 才走 `window.open(..., '_blank')`。详见 README §5.1。

**手工核对**（SSH 进飞牛）：

```bash
su - postgres -c "psql -d appcenter -c \"select service_name,type from app_service \
  where app_id = (select id from app where app_name = 'fnos-dwg-viewer')\""
# 期望：type 全是 url；若是 iframe 说明 fix-open-type 没生效
```

**看一眼脚本有没有跑过**：

```bash
grep fix-open-type "$TRIM_PKGVAR/app.log"      # 通常 /vol1/@appdata/fnos-dwg-viewer/app.log
```

日志里会有两种之一：

* `appcenter：打开方式已改为 url 型，桌面图标关联已清除` —— 正常；
* `找不到 psql，跳过…` / `⚠ appcenter 修正失败（ac 库结构可能已变），跳过` ——
  脚本**故意不报错也不让安装失败**（宁可少一个优化，也不能把应用装坏）。
  系统大版本升级后 `appcenter` / `trim_sac` 表结构变了就会出现这一条，
  这时按上面的 SQL 手工核对并按需手工 UPDATE。

> 桌面图标同理：`trim_sac` 库的 `entry`（`is_display` / `open_type`）与
> `user_desktop_entry` 才是前端桌面列表的数据源，**只删 `appcenter.app_shortcut`
> 图标不会掉**。

**桌面上还留着一个点不开的图标？** 确认 `manifest` 里 `desktop_applaunchname`
的值是**空的**（fnpack 会无条件写出这个键，值空才是对的），再重装一次让
`fix-open-type` 清 `trim_sac`。
